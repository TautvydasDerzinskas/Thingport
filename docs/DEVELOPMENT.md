# Development

How to run Thingport locally with hot reload, so you can work _on_ it. If you just want to run an
instance, follow the Docker Compose instructions in the [README](../README.md) instead.

## What's in the repo

| Directory    | What it is                                                                   |
| ------------ | ---------------------------------------------------------------------------- |
| `backend/`   | Express + Prisma API (TypeScript). Serves everything under `/api/*`.         |
| `frontend/`  | React + Vite single-page app.                                                |
| `extension/` | "Thingport Grab" browser extension -- TypeScript + SCSS, built with esbuild. |
| `bridge/`    | Slicer bridge helper app (Go).                                               |
| `docs/`      | This documentation.                                                          |

## Prerequisites

- **Node.js 24 or newer.** The root `.nvmrc` says 24 (`nvm use` picks it up), and CI and the Docker images run on it.
- **Docker**, to run Postgres. Everything else runs natively so you get hot reload.
- **Go 1.21+** -- only if you're changing `bridge/`.

## 1. Install dependencies

```bash
git clone https://github.com/TautvydasDerzinskas/Thingport.git
cd Thingport

npm install # root -- installs the husky pre-commit hook
npm --prefix backend ci
npm --prefix frontend ci
```

Each project has its own `package-lock.json`; there is no workspace root tying them together.

## 2. Start Postgres

The `db` service in `docker-compose.yml` has **no host port mapping** on purpose -- it's only
reachable from inside the Compose network, so a natively-run backend cannot connect to it. Run
your own container for development:

```bash
docker run -d --name thingport-db \
  -e POSTGRES_USER=thingport \
  -e POSTGRES_PASSWORD=thingport \
  -e POSTGRES_DB=thingport_dev \
  -p 5432:5432 \
  postgres:16-alpine
```

If something already listens on 5432, map a different host port and adjust `DATABASE_URL` below.

## 3. Configure the backend

```bash
cp backend/.env.example backend/.env
```

`backend/.env.example` is written for the Docker Compose deployment, so two values **must** change
for local development:

| Variable       | Set it to                                                                     | Why                                                                                                    |
| -------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL` | `postgresql://thingport:thingport@localhost:5432/thingport_dev?schema=public` | The example points at `db:5432` -- the Compose service hostname, which doesn't resolve outside Docker. |
| `FILE_STORAGE` | an absolute or relative path you own, e.g. `./storage`                        | The example uses `/app/storage`, the path inside the container.                                        |

Also set `AUTH_SECRET` to any non-empty random string -- it signs login tokens, and the example
value is a placeholder.

Leave `API_PORT=8000`. The Vite dev server proxies `/api` to `http://localhost:8000`
(`frontend/vite.config.js`), so changing one means changing both.

`backend/.env` is gitignored. Never commit it.

## 4. Create the database schema

```bash
cd backend
npm run prisma:generate   # required -- there is no postinstall hook, so the client isn't generated by `npm ci`
npx prisma migrate deploy # applies the 27 committed migrations
```

## 5. Run it

In two terminals:

```bash
npm --prefix backend run dev  # tsx watch  -> http://localhost:8000
npm --prefix frontend run dev # vite --host -> http://localhost:5173
```

Open <http://localhost:5173>. **The first account you register becomes the admin** -- see
`backend/src/routes/auth.ts`, which bootstraps the first user as `ADMIN` and everyone after as
`MEMBER`.

## Tools

Run from the checkout, the backend offers the tools in its own [`tools`](../tools) folder under **Administration →
Tools**, not the repository's on GitHub, and reads them afresh on each visit: change a tool, refresh, and **Update**
takes the change. The local `docker-compose.yml` mounts the folder for the same. See the [tools guide](guides/tools.md)
for using them, and [tool development](TOOL_DEVELOPMENT.md) for writing one.

## Optional: FlareSolverr

Thingiverse and MyMiniFactory sit behind Cloudflare, and some imports need FlareSolverr to get through. It's optional --
without it those imports will simply fail.

```bash
docker run -d --name thingport-flaresolverr -p 8191:8191 ghcr.io/flaresolverr/flaresolverr:latest
```

Then set its URL (`http://localhost:8191`, with or without `/v1`) in **Administration → Connections →
FlareSolverr**. `FLARESOLVERR_URL` in `backend/.env` is copied into that setting on the first startup; after that the
saved value wins and the env var is ignored.

## Running the tests

### Backend

19 test files, 151 tests. They run against a **real Postgres database**, registering accounts and
creating and deleting rows as they go.

> [!WARNING]
> `backend/.env` is your development instance's. The suite won't take its database: it stops unless
> `DATABASE_URL` is set on the command line. It doesn't take its storage folder or FlareSolverr
> either; files go to `thingport-test-storage` in the system temp folder unless `FILE_STORAGE` says
> otherwise (see `backend/tests/setup.ts`).

```bash
docker run -d --name thingport-test-db \
  -e POSTGRES_USER=thingport -e POSTGRES_PASSWORD=thingport -e POSTGRES_DB=thingport_test \
  -p 55432:5432 postgres:16-alpine

cd backend
export TEST_DB="postgresql://thingport:thingport@localhost:55432/thingport_test?schema=public"

DATABASE_URL="$TEST_DB" npx prisma migrate deploy
DATABASE_URL="$TEST_DB" npm test
```

The suite takes about 30 seconds. It runs test files sequentially on purpose -- several files
mutate the same global `Setting` rows, and parallel workers race each other. See the comment in
`backend/vitest.config.ts`.

### Frontend

`npm run test:run` in `frontend/` runs the tests with Vitest, and `npm run verify` adds the type check, lint and build.
They run without a DOM: components are rendered to static markup and read as text (see
`frontend/src/components/importQueue/testing.tsx`).

### Regression pack

Playwright scenarios in `regression/` that drive the real app in Chromium: sign-up, sign-in,
uploading (single and multiple files, zips, folder trees), the consume folder, the import queue, collections, and the
sidebar (navigation, the admin-only route, bookmarks and their drag-to-reorder, collapsing). Upload
fixtures are generated in `tests/fixtures.ts` rather than checked in. The consume folder is
`regression/consume/`, bind-mounted into the backend for the run. MakerWorld links import with no network:
`fixtures/fake-provider.cjs`, preloaded into the backend for the run, answers their calls, and the first digit of a
model's id says whether it imports at once, waits for a test to let it go, or fails. `run.sh` builds the backend and
frontend images from your checkout, starts them with Postgres on port 8090, runs the scenarios, and
then removes the stack. The database and storage live on tmpfs, so every run starts empty and leaves nothing behind.
It never touches your development database. It needs Docker.

```bash
cd regression
npm install
npx playwright install chromium
./run.sh                      # whole pack
./run.sh tests/models.spec.ts # extra arguments go to `playwright test`
```

CI runs it every Saturday at 00:00 UTC (`.github/workflows/regression.yml`). You can also start it
from the Actions tab. When it fails, the HTML report, traces and container logs are uploaded as the
`regression-report` artifact.

> [!IMPORTANT]
> **A test that ends a session needs a session of its own, and one that changes the password or deletes the
> account needs an account of its own.** The pack signs in once, in `tests/admin.setup.ts`, and every spec replays
> that one token. The backend reads the session row on every request (`backend/src/auth.ts`), so a revoked token
> stays revoked, and each spec that runs later -- files go in alphabetical order, one at a time -- fails with a 401
> or sits waiting for a page that has bounced to the sign-in form. Signing out ends only the session it's done in:
> `logs out` in `tests/auth.spec.ts` is the worked example: it sits in the `signed out` group, which starts from an
> empty storage state, and signs in first so it has a session to end. A separate storage state isn't enough for
> the other two, though: changing the password signs the account out everywhere else, and deleting it takes every
> session with it. Register an account for those, as `tests/consume.spec.ts` does.

### App screenshots

The README and website screenshots in `frontend/src/assets/screenshots/` are captured from a running
instance with a populated library, by `regression/screenshots.mjs` (the extension's screenshots
aren't covered). It signs in, captures every shot in the light and the dark theme at 1400×790 and 2× scale,
and overwrites the files in `light/` and `dark/`. The account's theme and Categories/Folders choice are switched
for the shots and restored afterwards, and a shot that can't be taken is reported without stopping the run. The import
queue's rows are made up and answered in the browser, so nothing is queued on the instance.

```bash
cd regression
THINGPORT_PASSWORD='…' npm run screenshots -- --url https://thingport.example --email you@example.com \
  --model <id> --quality-model <id> --ai-description-model <id>
npm run screenshots -- --url … --email … --only 03,04     # just some shots
```

Models are named by id: one for the details and 3D preview shots, one whose print quality check found problems,
and one whose description AI rewrote (that shot is skipped without it). The customizer and collection sync shots
take the library's first model with a script and first synced collection, unless `--generative-model` or
`--synced-collection` names another.

`--out` writes somewhere else instead, e.g. to compare before replacing. Self-signed certificates
are accepted.

### Release notes pictures

The What's new pictures are a different set: cropped to the thing each one is about, WebP, and named after the
release. `regression/release-shots.mjs` captures them from a running instance into `release-notes/screenshots/`,
the same way, and skips the shots whose tool isn't installed or whose model wasn't named rather than failing the
run.

```bash
cd regression
THINGPORT_PASSWORD='…' npm run release-shots -- --url https://thingport.example --email you@example.com \
  --model <a multicolour model> --generative-model <a model that came with its script>
npm run release-shots -- --url … --email … --only tools,admin-tools   # just some shots
```

A shot's file is what an item's `images` then names, so the two are written together -- an item naming a picture
nothing captures leaves a gap in the dialog. Thingport Grab's own pictures come from
`npm --prefix extension run screenshots` instead, and are converted to WebP by hand.

The editor shots (`tools-ai`, `tool-editor`) need **Users' own tools**, a setting for the whole instance. If it's off
the script turns it on for the run, so everyone who sees tools can make their own meanwhile, and off again at the end.
A run stopped with Ctrl+C or killed leaves it on, so check **Administration → Tools** after one.

## Quality checks

| Command                               | What it runs                     |
| ------------------------------------- | -------------------------------- |
| `npm run format`                      | Prettier, gofmt, `prisma format` |
| `npm run format:check`                | the same, check only (CI)        |
| `npm --prefix backend run lint`       | oxlint                           |
| `npm --prefix frontend run lint`      | oxlint                           |
| `npm --prefix frontend run typecheck` | `tsc --noEmit`                   |
| `npm --prefix frontend run verify`    | typecheck + lint + tests + build |

A husky pre-commit hook formats staged files and runs oxlint over whichever project you touched (see
`lint-staged.config.js`). It does **not** typecheck, so run `typecheck` yourself before pushing
frontend changes -- CI will.

## Extension

```bash
cd extension
npm install
npm run dev # watch build into dist/chrome (npm run dev:firefox for dist/firefox)
```

- **Chrome / Edge**: `chrome://extensions` -> enable **Developer mode** -> **Load unpacked** -> select `extension/dist/chrome`.
- **Firefox**: `about:debugging#/runtime/this-firefox` -> **Load Temporary Add-on** -> select `extension/dist/firefox/manifest.json`.

Reload the extension after each rebuild, and point it at `http://localhost:5173` in the popup.
Chrome and Edge run the background bundle as a service worker while Firefox runs it as an event
page -- if you add top-level code there, make sure it works in both. See
[extension/CONTRIBUTING.md](../extension/CONTRIBUTING.md) for the code layout, the per-browser
builds, the store zips and the screenshot generator.

## System notifications

Announcements for every instance, such as a known bug or a new feature, live in
[`system-notifications.json`](../system-notifications.json) at the repo root. Each backend fetches it
from `main` at startup and every 6 hours, and sends each entry once to each user it's meant for, as an
ordinary notification (the System tab). To post one, add an entry to `entries` and merge it:

```json
{
  "entries": [
    {
      "id": "2026-10-imports-fail-on-printables",
      "title": "Printables imports fail since Oct 10",
      "body": "Printables changed its API. A fix is on the way; update when it lands.",
      "url": "https://github.com/TautvydasDerzinskas/Thingport/issues/123",
      "published_at": "2026-10-11T12:00:00Z",
      "audience": "admins",
      "version": "<1.2.0"
    }
  ]
}
```

- `id` must be unique and never reused: it's what stops an entry being sent twice.
- `body` and `url` are optional; `url` must be `https://`, and the notification shows its domain.
- `path` is an optional in-app page opened on click, e.g. `/admin`.
- `published_at` is the date shown; a future date waits until then.
- `audience` is `admins` (the default) or `all` for every user.
- `version` limits it to instances on certain versions: `1.2.0` exactly, or `<`, `<=`, `>`, `>=` a
  version. Leave it out for all versions. An instance that later updates into the range still gets it.
- Versions before 1.0.0 read only the `notifications` list and ignore `version`, so add there only what
  every one of them should get; everything else goes in `entries`.
- Entries older than 90 days aren't sent, so old ones can stay in the file or be removed.
- `SYSTEM_NOTIFICATIONS_URL` points a backend at another file; an empty value turns fetching off.

An entry past those 90 days is spent: no instance will ever be sent it again. Move it to
[`system-notifications-archive.json`](../system-notifications-archive.json), which nothing fetches, rather than
deleting it -- the record of what was announced is worth keeping, and an `id` must never be reused. Until an entry
is that old, leave it where it is: an instance that has been off for a month still has it coming.

## Release notes (What's new)

The first time a backend starts on a newer version than it last ran, every user gets a notification that opens
the What's new dialog (admins can reopen it from Update Checker in Administration). A fresh installation doesn't get this notification. There's no need to add a "Welcome to
X.Y.Z" entry to `system-notifications.json` for this any more.

The dialog fetches its content from `main`, so it can be written after the release is out:

1. [`release-notes/latest-release-notes.json`](../release-notes/latest-release-notes.json) when its `version` is the
   instance's backend version.
2. Otherwise `backend/CHANGELOG.md` for that version, with the `frontend/CHANGELOG.md` release that went out with
   it. An instance that skipped versions gets every release since the one it ran before, up to five.

To write the notes for a release, first copy the current file into
[`release-notes/archive/`](../release-notes/archive) under the version it names, so the release it describes isn't
lost when the file is overwritten:

```bash
cp release-notes/latest-release-notes.json "release-notes/archive/$(node -p 'require("./release-notes/latest-release-notes.json").version').json"
```

Nothing reads the archive -- an instance that skipped a release still falls back to `CHANGELOG.md` for the ones in
between -- and an archived file's `images` stay relative to `release-notes/`, where they were read from. Then
replace the file's contents:

```json
{
  "version": "1.2.0",
  "title": "Optional headline",
  "summary": "Optional sentence or two under it.",
  "items": [
    {
      "type": "feature",
      "highlight": true,
      "title": "Pick an accent colour",
      "description": "Optional detail.",
      "code": "claude mcp add ...",
      "images": [{ "src": "screenshots/1.2.0-accent.webp", "caption": "Optional caption" }],
      "url": "https://github.com/TautvydasDerzinskas/Thingport/pull/123"
    }
  ]
}
```

- `type` is `breaking`, `feature`, `improvement` or `fix`; the dialog groups them in that order.
- `highlight: true` shows the item as a large card above the grouped list; keep it to the release's headline
  features.
- `code` is a command shown in a box with a copy button, e.g. how to connect something.
- `images` are relative to the file (put them in `release-notes/screenshots/`, named after the version) or full
  `https://` URLs; up to six per item. Crop them to the control being shown rather than the whole page; WebP keeps them
  small. Everything but `type` and `title` is optional.
- A file that doesn't parse falls back to the changelog, as does one naming a version outside the running
  release's `x.y` line. One naming an earlier patch of that line still counts, for the quiet hotfixes below.
- `RELEASE_NOTES_URL` points a backend at another copy of the repo files; an empty value turns fetching off.

To update without telling anyone, e.g. a hotfix straight after a release, add its version to
[`release-notes/quiet-releases.json`](../release-notes/quiet-releases.json) in the same release PR, so it's on `main`
before instances update:

```json
{ "versions": ["1.2.1"] }
```

No notification is sent to an instance that already heard about the release the hotfix follows, and the next release's
What's new also covers what the quiet one changed. An instance further back is still told, so a quiet hotfix never
swallows notes nobody has seen: coming from 1.1.0 straight to 1.2.1 announces as usual, with What's new starting at
1.1.0. Leave `latest-release-notes.json` naming 1.2.0 for this -- a curated file is shown by a later patch of the same
`x.y` line, so those notes are what that instance reads. If the file can't be read when an instance starts, the update
is announced as usual.

An entry can say where it is quiet from, which is its own `x.y.0` by default:

```json
{ "versions": [{ "version": "1.2.1", "quietFrom": "1.2.1" }] }
```

`quietFrom` at the version itself keeps it quiet for everyone, however far back they are -- as does listing an `x.y.0`,
which has no earlier release of its line to miss.
